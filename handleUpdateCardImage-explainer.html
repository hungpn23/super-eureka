Giải thích hàm handleUpdateCardImage

File này chỉ phục vụ cho việc mô tả. Mục tiêu là giúp bạn đọc và hiểu vì sao hàm này trước đó nhìn rất lặp, phần nào là lặp hợp lý, và phần nào đã được refactor để dễ đọc hơn.

Kết luận ngắn gọn: hàm này khó đọc vì nó đang xử lý một tác vụ bất đồng bộ có rủi ro race condition. Vì vậy nó buộc phải kiểm tra lại card hiện tại ở nhiều điểm khác nhau.

1. Hàm này làm gì?

Hàm handleUpdateCardImage xử lý lúc user chọn hoặc bỏ ảnh cho một card trong màn hình tạo deck.

  • Nếu user bỏ ảnh, nó reset trạng thái ảnh của card.
  • Nếu user chọn ảnh, nó gọi API upload.
  • Khi upload thành công, nó lấy fileId từ backend.
  • Nếu upload lỗi, nó dọn lại state và hiện toast báo lỗi.
Hàm này không chỉ “upload file”. Nó còn phải đảm bảo không ghi nhầm kết quả upload cũ vào card khi user thao tác quá nhanh.

2. Vì sao trước đó nhìn bị lặp code nhiều?

Lặp hợp lý

Đây là phần lặp bắt buộc vì có nhiều nhánh chạy sau await:

  • nhánh thành công
  • nhánh lỗi
  • nhánh cleanup trong finally

Mỗi nhánh đều phải tự hỏi lại: “card này còn đúng là card đang upload request này không?”

Lặp dư thừa

Trước khi refactor, có cả phần lặp lookup card và lặp guard check do chưa gom thành helper. Phần này không làm sai logic, nhưng làm code dài và khó đọc.

3. Hãy hiểu vấn đề cốt lõi: race condition

Hãy tưởng tượng user thao tác rất nhanh trên cùng một card:

  1. Chọn ảnh A.
  2. Frontend bắt đầu upload A với request id là R1.
  3. Trước khi A upload xong, user chọn tiếp ảnh B.
  4. Frontend bắt đầu upload B với request id là R2.
  5. Request A trả về muộn hơn request B.

Nếu không có guard, response của A có thể ghi đè state của B. Khi đó:

  • card đang hiển thị ảnh B
  • nhưng fileId lại là của ảnh A

Đó là lý do code phải check lại imageUploadRequestId === requestId trước khi sửa state.

4. Cách đọc hàm theo đúng thứ tự

Bước 1. Nếu không có file thì reset

Dòng đầu tiên kiểm tra payload.file. Nếu user vừa bỏ ảnh hoặc clear file input, không cần upload gì cả. Lúc đó chỉ cần gọi resetCardImage(cardId).

Bước 2. Tìm đúng card

Code dùng cardId để tìm card trong createState.cards. Nếu không tìm thấy thì dừng luôn. Bước này là để chắc chắn ta đang làm việc đúng card.

Bước 3. Tạo request id mới

Mỗi lần upload ảnh đều tạo một requestId mới. Đây là mấu chốt để phân biệt request nào là request hiện hành của card.

Bước 4. Đánh dấu card đang upload

Trước khi gọi API, card được cập nhật state:

  • fileId = undefined
  • imageFile = payload.file
  • isUploadingImage = true
  • imageUploadRequestId = requestId

Mục đích là để UI biết card đang upload và mọi response cũ phải bị coi là hết hạn.

Bước 5. Gọi API upload

File được đưa vào FormData với field card-image, rồi gửi tới POST /api/decks/card-image.

Bước 6. Khi thành công, vẫn chưa được set state ngay

Đây là chỗ dễ nhầm nhất. API thành công không có nghĩa là được phép set fileId ngay.

Code phải hỏi lại:

  • card này còn tồn tại không?
  • request hiện tại có còn là request mới nhất của card không?

Chỉ khi cả hai điều kiện đúng thì mới được set currentCard.fileId = response.fileId.

Bước 7. Khi lỗi, vẫn phải check lại y hệt

Vì lỗi cũng có thể đến từ một request cũ. Nếu request đó đã hết hạn rồi mà vẫn xóa state hiện tại, UI sẽ bị sai.

Bước 8. Trong finally, vẫn phải check lại lần nữa

finally luôn chạy, dù request success hay error. Vì vậy nếu không kiểm tra lại request id, một request cũ có thể tắt cờ isUploadingImage của request mới hơn.

5. Vì sao refactor bằng helper lại dễ hiểu hơn?

Sau khi refactor, ta tách 2 helper:

Helper Nhiệm vụ Lý do cần có
getCardById(cardId) Tìm card theo tempId Tránh lặp find(...) ở nhiều chỗ
getCurrentUploadingCard(cardId, requestId) Vừa tìm card, vừa xác nhận card đang gắn với đúng request hiện tại Gom phần guard quan trọng nhất vào một nơi để tránh copy-paste
Sau refactor, logic cũ không đổi. Chỉ là thay vì lặp cả cụm “find card + check request id” ở nhiều nơi, code gọi helper để diễn đạt ý đó bằng một tên hàm.

7. Câu chốt dễ nhớ nhất

Hàm này nhìn lặp không phải vì logic upload khó, mà vì logic bảo vệ state khỏi request cũ mới là phần chính.

Mỗi chỗ có thể sửa state sau await đều phải tự hỏi lại: “request này còn là request hợp lệ mới nhất của card này không?”
